# S2: latencia de SyncTeX, CLI contra parser propio

**Decisión: parser propio en Rust como camino principal; el CLI `synctex` queda como oráculo de los tests y como fallback si el parser falla.** El CLI no llega al objetivo de F4 (≤ 150 ms por salto) en ningún PDF del libro: tarda de 320 a 590 ms por llamada. El parser carga el archivo una vez por build (8 a 47 ms) y responde en microsegundos.

## Qué se probó

`spikes/s2-synctex/` (crate Rust con `flate2`, `cargo build --release`) sobre el `.synctex.gz` del libro completo (194 páginas, 1,6 MB comprimido, 9,5 MB descomprimido, 313.585 nodos, 254 archivos de entrada).

- **Parser propio** (`src/synctex.rs`): lee el formato `SyncTeX Version:1`, guarda los nodos con su padre y el fin de su caja, e indexa por (archivo, línea) para el forward y por página para el inverse.
- **Consultas:** 50 líneas de párrafos de los capítulos, al azar con semilla fija (`gen-queries.mjs`), para el forward. Para el inverse, 50 puntos "x,y" que devuelve el propio CLI para esas líneas (la ida y vuelta real) y 25 puntos al azar sobre la página.
- **CLI:** `synctex view -i línea:0:archivo -o pdf` y `synctex edit -o página:x:y:pdf`, una llamada por consulta, con reloj de pared (incluye lanzar el proceso).
- **En proceso:** cada consulta repetida 300 veces, promedio en µs.

## Qué se midió

| | Parser propio | CLI `synctex` |
|---|---|---|
| Carga del PDF completo (gunzip 20 ms + parseo 16 ms + índices 11 ms) | **47 ms** (5 cargas: 47 a 50) | n/a: lo repite en cada llamada |
| Carga de `libro_fast` (200 mil nodos) / `cap_actual` (48 mil) | 34 ms / 8 ms | |
| Memoria con el libro completo cargado | **+18 MB** (4 → 22 MB) | |
| Forward, 50 consultas | media 0,5 µs, p95 1,0, máx 1,5 µs | media **485 ms**, p50 469, p95 582, máx 599 ms |
| Inverse, 75 consultas | media 1,9 µs, p95 3,9, máx 5,1 µs | media **478 ms**, p50 467, p95 574, máx 594 ms |
| CLI por llamada, según el PDF (5 llamadas, mediana) | | `cap_actual` 319 ms, `libro_fast` 415 ms, completo 472 ms |

El costo del CLI es casi todo fijo (319 ms con el SyncTeX más chico, 5 veces menor que el completo): lanzar `synctex.exe` y releer el archivo cuesta más que cualquier consulta. Con el parser, el salto completo queda en el costo de cargar el archivo la primera vez después de cada build (8 a 47 ms) más microsegundos.

### Concordancia con el CLI

| Consulta | Resultado |
|---|---|
| Forward: mismo conjunto de páginas | **50/50** |
| Forward: la primera caja del CLI está entre las propias (±2 bp) | **46/50** |
| Inverse, ida y vuelta en **líneas de texto** (23 de las 50 consultas): misma línea que el CLI | **21/23** (91 %) |
| Inverse, ida y vuelta en todas (incluye figuras y ecuaciones): misma línea | 22/50 |
| Inverse, los 75 puntos (incluye 25 al azar): misma línea / a ±1 / a ±5 | 34 / 41 / 55 de 75 |

El parser acierta donde importa para el libro (párrafos de una línea larga), y todavía no replica al CLI en figuras, ecuaciones y puntos sueltos de la página. Esos desacuerdos son de criterio (qué hijo o qué caja elige el CLI), no de formato. Se retoma en F4 con el CLI como oráculo, que es lo que el plan ya prevé.

## Cosas del formato que no estaban en el plan

- **Los `Input:` no están sólo en la cabecera.** TeX declara cada archivo la primera vez que lo abre, así que 50 de los 254 aparecen en medio del contenido. Un parser que lea sólo la cabecera pierde esos archivos (a mí me pasó: 204 en vez de 254, y las consultas a esos archivos no encontraban nada).
- **La caja de un párrafo y sus hijos no tienen la misma línea.** La caja (`(214,230:...`) lleva la línea donde TeX terminó de armarla, la siguiente al párrafo, y los hijos (`k214,229:...`) llevan la del texto. El forward tiene que buscar en las hojas y devolver la caja que las contiene; el inverse tiene que refinar mirando los hijos.
- **Los registros `x` (posición actual) hay que ignorarlos al refinar el inverse.** El primero de cada línea de texto trae la línea siguiente y, por estar pegado al borde izquierdo, ganaba siempre: el cursor caía una línea más abajo (1555 en vez de 1554). Con ese ajuste, el 91 % de arriba.
- **El CLI informa `v` como el borde inferior de la caja** (línea de base más profundidad), no la línea de base.
- **Una caja de tamaño cero** (la sangría de un párrafo, una figura externalizada) se resuelve a la primera caja contenedora con tamaño: lo que el CLI devuelve para una figura es el rectángulo de la figura (277×224 bp), no el nodo vacío.
- Posiciones en sp absolutos desde arriba a la izquierda; `bp = sp / 65781,76` con `Unit:1` y `Magnification:1000`.
- Las rutas de entrada son absolutas con el nombre del archivo en UTF-8: la comparación tiene que normalizar `\` y `/` y mayúsculas.

## Qué cambia del plan

6.1: el parser propio queda decidido (con los números de arriba) y el CLI queda como oráculo y fallback. Ver `plan.md`. Los criterios de aceptación de F4 no cambian: ≤ 150 ms por salto es alcanzable con el parser y no con el CLI.
